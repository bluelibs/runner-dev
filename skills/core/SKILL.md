## Durable dashboard

The docs sidebar exposes **Durable** only when the backend's `/docs/data` payload has `hasDurable: true`, based on discovered application runtimes; absent/false availability and static catalogs hide the link. It navigates to `/durable`. `/durable` is an isolated live-only Studio page that uses existing application durable runtimes and the server's Host/password guards. `/durable/api` is REST, outside GraphQL/MCP. Scope every request with the selected `runtimeId`; never create a second runtime or assume global workflow discovery establishes ownership. Use public `DurableResource`/operator APIs and real signal definitions for validation. Keep core Runner 6.6 compatibility; lifecycle/state controls require advertised runtime capabilities. Audit remains application-owned and optional; repair reasons go to DevTools logs because Runner 6.6 does not expose a public audit-write boundary. Retry must reject cancelled executions because Runner 6.6 retains their cancellation state. Observed timelines must not invent future branches. When signal metadata is omitted, an observed signal wait supplies its registered event ID for the dialog. `metadata.studio.presets` can supply named start inputs. Keep docs and dashboard bundles separate so static docs exports remain self-contained. Use `npm run play:durable` after building the UI for a real-runtime local preview.

## Telemetry persistence

`dev.with({ maxEntries, persistence: resources.sqlitePersistence.with({ file }) })` retains all four live categories across restarts; `resources.live.with()` accepts the same config. SQLite is loaded lazily from Node's built-in `node:sqlite` (22.13+ or 24+, or the experimental flag on 22.5–22.12). Use a stable, gitignored path and one database per runtime. Each SQLite store owns a worker thread for opening/restoration/batched SQL/closing; recording synchronously snapshots and enqueues before publishing. Queues hold at most 10,000 pending/in-flight entries, flush every second or at 1000 entries, and commit each batch atomically with eviction. Full queues reject entries; write failures latch and surface via status/recording/flush/close. Graceful disposal drains; abrupt termination may lose pending records. Direct factory users must await load() and close(); flush() acknowledges commits. The cap applies per category on disk and in memory, including a lower cap on restart. Restoration preserves sequences and resumes above the committed maximum; GraphQL/SSE use existing read APIs.

Like Runner cache providers, persistence resource definitions or configured `.with(...)` entries are auto-registered and injected through config-driven dependencies. Their initialized value must be a `LivePersistence` store; DI, overrides and isolation work normally. The resource owns initialization and disposal, and is disposed after the live service stops. `sqlitePersistenceResource` names the built-in resource export. `sqlitePersistence({ file })` creates a closeable store for custom resource wiring. `LivePersistenceResource`/`LivePersistenceSource` type the resource/config option. Avoid provider dependencies on live itself (cycles).

Custom resources return `LivePersistence` directly: sync or async `load({ maxEntries })` trims every category and returns ascending `{ kind, entry }` records plus the highest committed `lastSequence` (including evicted records). Synchronous `append(record, { maxEntries })` returns `undefined`, accepting an atomic commit or immutable snapshot into a bounded queue, or throws. Buffered providers drain on disposal and expose failures; returning a promise from append is rejected by types and guarded at runtime. Invalid provider values and snapshots fail startup. Resource `init()` may be async and must clean up partial initialization on failure; Runner calls `dispose()` for initialized providers when restoration fails or the runtime shuts down. Validate records before committing; SQLite validates serialized snapshots to prevent invalid entries from poisoning restarts. SQLite payloads are JSON snapshots, with explicit string representations for bigint/symbols/functions/circular references. Read the compact guide and README persistence sections before changing this contract.

## Scaffold dependency checks

New projects target Runner 6.6 and Vitest 4.1.11+ and require Node.js 22.12+ or 24+ (runner-dev itself needs Node.js 22+). Their `npm run dev` (`tsx watch`) does not set `NODE_ENV`, so the docs UI shell, file editing, `swapTask` and `eval` stay off there until the app is started with `RUNNER_DEV_EVAL=1` or `NODE_ENV=development`. Run `npm run audit` in generated projects to check production and development dependencies. Before a release, run `npm run build`, `npm run audit`, and `npm run audit:scaffold`; the latter verifies a fresh project against the packed local release, including its build and tests. The repository audit covers backend dependencies and frontend tooling. Do not suppress audit findings or use `--omit=dev` for this check. `npm run check:runtime-deps` (run by CI after the build and by `npm pack` after a clean build) fails when `dist` requires a package that is not a dependency or peer, or when loading the package entry pulls in an optional peer such as `typescript`.

Runner 6.6 durable apps must register `resources.durable` (also exported as `durableSupportResource`) from `@bluelibs/runner/node` alongside the durable runtime; the workflow tag alone does not register the required runtime tags, events, and lifecycle hook.

## Task and hook performance (APM)

Opt in with `dev.with({ apm: true })` or `resources.live.with({ apm: true })`. The Telemetry tab separates task performance and hook reactions; Logs provides dedicated log inspection. Live retains its original layout. Nonzero failure rates open retained errors; correlation IDs link to trace and logs. Details start with the latest 50 matching runs/errors; infinite scrolling loads older pages with a virtualized list and traces load up to 200 records per category; aggregate history may outlast details. APM has independent bounded samples, exact nearest-rank p50/p95/p99, failure rates and all/direct/nested scopes. Inclusive timings overlap for delegated work; task and hook counts/percentiles remain separate. Tasks delegated by hooks retain the hook as their trace parent. Query `tasks { taskId count p95Ms }` and `hooks { hookId count p95Ms }` on the APM snapshot. The sample cap is shared by tasks and hooks. SQLite is automatic when the builtin is available (`./.runner-dev/apm.sqlite`); otherwise memory. `apm: { storage: "memory", maxSamples: 10000 }` avoids disk writes. Database errors throw; use one gitignored file per runtime. No payloads, error text or correlation IDs are persisted. Query `live.apm(windowMinutes: 30, scope: all)`; windows are 1–525600 minutes and the cap may truncate them. Read the README/compact-guide APM section for the full contract.

APM retention is configured once under `apm`: `retentionDays: 7`, `maxStorage: "1mb"`, optional `maxSamples` and ISO `cutoffDate`. The same day/count/byte policy applies to memory, SQLite, ClickHouse and Redis. Size strings use binary units; the minimum budget is 512 KiB, measuring compact UTF-8 samples rather than physical files, queues or object overhead. Without bytes the count defaults to 10,000; with bytes it has a 10,000,000 safety ceiling unless configured lower. `resources.clickHouseApmPersistence.with({ url, streamId })` uses native HTTP without an extra dependency; `resources.redisApmPersistence.with({ url, streamId })` lazily loads optional `ioredis`. Credentials use provider-specific environment variables. One active runtime per stream/file. SQLite APM and live history run their batched SQL in separate worker threads; APM migrates old samples. Background queues are bounded, failures are visible, and graceful disposal flushes; abrupt termination may lose pending writes. Custom providers receive normalized byte/day/count/date policy through async `load` and implement enqueue-only `append` plus async `flush`. See README for retention and database housekeeping details, and [the performance report](references/readmes/TELEMETRY_PERFORMANCE.md) for measured overhead.
